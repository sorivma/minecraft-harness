## Purpose

Показывать полный доступный ход работы агента внутри Minecraft: от потокового ответа и поиска до инструментов, решений пользователя и результата.

## ADDED Requirements

### Requirement: Structured live timeline
UI SHALL показывать отдельные обновляемые элементы сообщений, плана, доступных summaries, web activity, инструментов, команд, изменений файлов, дочерних задач, review и compaction, когда backend предоставляет соответствующие события. Состояния ожидания, выполнения, успеха, ошибки, прерывания и отключения SHALL быть различимы. UI MUST NOT выдумывать отсутствующие события или скрытые рассуждения.

#### Scenario: Full agent workflow
- **WHEN** агент сообщает прогресс, ищет в интернете, вызывает инструмент, изменяет файл и завершает ответ
- **THEN** лента последовательно показывает все эти действия с собственными статусами и итоговым ответом без необходимости читать сырой JSON

#### Scenario: Final snapshot after streaming
- **WHEN** после потоковых фрагментов приходит итоговый элемент
- **THEN** существующая карточка обновляется окончательными данными без дублирования текста или действия

### Requirement: Browsing and tools detail
Web-карточки SHALL показывать доступные запросы, посещаемые страницы и источники. Карточки инструментов SHALL показывать имя, сервер, аргументы, прогресс и результат/ошибку, когда эти данные предоставлены. Длинные подробности SHALL раскрываться и копироваться; ссылки SHALL быть доступны для открытия.

#### Scenario: Search followed by page access
- **WHEN** backend сообщает поиск, открытие страницы и поиск текста на странице
- **THEN** UI различает эти действия и показывает переданные запросы/URL, не ограничиваясь общим статусом «работает»

#### Scenario: MCP tool fails
- **WHEN** инструмент передал прогресс и затем ошибку
- **THEN** карточка сохраняет полученные сведения и показывает ошибку вместо успешного завершения

### Requirement: Execution and changes inspection
UI SHALL предоставлять потоковый вывод команд, доступные cwd/exit code и просмотр изменений по файлам с diff. План и дочерние задачи SHALL показывать собственные статусы, если они предоставлены backend.

#### Scenario: Inspect output and diff
- **WHEN** команда завершается и агент изменяет несколько файлов
- **THEN** пользователь может раскрыть вывод команды и изменения каждого файла, не теряя текущий черновик

### Requirement: Inline interaction requests
Подтверждения, вопросы с вариантами/свободным вводом и поддерживаемые формы MCP SHALL отображаться как интерактивные карточки своего диалога. Ответ SHALL отправляться только явным действием и ровно одному запросу. Закрытие панели MUST NOT означать согласие или отказ.

#### Scenario: Resolve a background approval
- **WHEN** фоновый диалог требует решения, пользователь открывает его и выбирает вариант
- **THEN** ответ получает исходный запрос, а другие диалоги и запросы не изменяются

#### Scenario: Double click or resolved request
- **WHEN** пользователь повторно нажимает ответ либо запрос уже разрешён сервером
- **THEN** повторный ответ не отправляется, и карточка показывает актуальное состояние

#### Scenario: Answer a question
- **WHEN** агент запрашивает выбор или текст через поддерживаемую форму
- **THEN** UI позволяет заполнить и отправить ответ без slash-команды и возвращает ошибки проверки рядом с полем

### Requirement: Unknown event and request handling
Неизвестное информационное событие SHALL иметь безопасное общее представление. Неподдерживаемый обязательный запрос SHALL получить явный протокольно корректный отказ/ошибку без автоматического разрешения и бесконечного ожидания.

#### Scenario: New request type
- **WHEN** backend получает запрос, который не может представить через текущий контракт
- **THEN** пользователь видит причину ограничения, а backend завершает запрос поддерживаемым ответом об ошибке
