## Context

См. `proposal.md`. Сейчас `CodexSession` объединяет транспорт, команды, один thread и строковую ленту; `CodexChatScreen` объединяет версионные API и всё поведение UI. `ClientHarness` владеет жизненным циклом мира. Общий код должен работать на Java 8.

Для проверки протокольной поверхности 2026-10-19 использован установленный `codex-cli 0.163.0`: `codex app-server generate-json-schema --out <temporary-directory>`. Экспорт содержит модели, управление threads, plan/reasoning notifications, MCP progress и интерактивные запросы. Наличие схемы не гарантирует доступность функции у аккаунта или runtime.

Официальные источники: [App Server](https://learn.chatgpt.com/docs/app-server), [Developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli). App Server предоставляет события элементов и их завершения, web search и запросы пользовательских решений. Команды CLI принадлежат его интерфейсу: не следует отправлять их как RPC или как текст агенту для имитации управления.

## Goals / Non-Goals

**Goals:** две независимые оси замены — версия Minecraft и агентный backend; полноценный интерактивный flow; проверяемый охват возможностей поддерживаемой версии Codex; отсутствие служебных команд в обязательном пользовательском пути.

**Non-Goals:** реализация дополнительных Minecraft-адаптеров или второго production backend в этом изменении; эмулятор терминала, встроенный браузер и собственная реализация инструментов Codex; перенос скрытого контекста разговора между разными провайдерами. UI показывает доступные события, не выдумывает скрытые рассуждения, проценты прогресса или источники.

## Decisions

### 1. Два независимых контракта

```text
forge-1.7.10 (composition root и платформенные операции)
   ├── chat-ui ────────────┐
   ├── core ───────────────┼── agent-api
   └── agent-codex ────────┘
        локальный процесс и JSON-RPC
```

- `agent-api`: только Java-типы контрактов, без Gson, Minecraft, рендеринга и Codex. Содержит `AgentBackend`, descriptors возможностей/моделей/действий, снимки диалогов, события, интерактивные запросы, ошибки и семантику жизненного цикла.
- `agent-codex`: запуск процесса, JSON-RPC, совместимость версий, перевод wire-типов в `agent-api`. Здесь располагается перенесённый `RpcConnection`; UI не получает JSON и имена RPC.
- `core`: рабочая область мира, каталог backend и диалогов, маршрутизация и восстановление состояния. Зависит только от `agent-api`; получает backend через конструктор/фабрику.
- `chat-ui`: состояние представления, компоновка, тема, редактирование текста, фокус, меню, лента. Зависит от `core` и `agent-api`, никогда от `agent-codex`.
- адаптер Minecraft собирает эти компоненты и реализует измерение текста, draw primitives, clipping, события ввода, clipboard, открытие URL и lifecycle. Компоновка и интеракции остаются общими.

Выделение только интерфейса поверх `CodexSession` оставило бы зависимость от Codex в моделях данных. Перенос только состояния UI оставил бы дублирование компоновки между версиями. Поэтому выделяются оба контракта полностью; готовая веб-панель не используется из-за интеграции и переноса на старые версии игры.

### 2. Семантика backend

Контракт поддерживает connect/disconnect, получение capabilities и моделей, пагинацию диалогов, создание/чтение/продолжение, отправку сообщения, прерывание, ответы на запросы и выполнение объявленных действий. Результаты асинхронны; backend не вызывает Minecraft. Core применяет события в одном последовательном цикле с ограниченным бюджетом на tick.

Идентификаторы непрозрачны и включают backend, workspace и поколение подключения; внутри диалога различаются turn, item и request. Ответ на запрос коррелируется также с исходным типом wire-id внутри адаптера. При отключении pending operations завершаются явной ошибкой, карточки становятся недоступны, поздние события старого соединения игнорируются.

Capabilities описывают доступность, ограничения и схемы параметров. Общие операции имеют строгие типы. Дополнительные действия используют нейтральные descriptors: строка, число, enum, boolean, выбор ресурса и составная форма. UI рендерит их без `if backend == Codex`. Неподдерживаемая форма даёт понятный статус и корректный отказ адаптера.

Замена backend — выбор адаптера для нового диалога или нового подключения. Существующий диалог навсегда привязан к исходному backend; смена не пересылает ему чужой контекст и не прерывает незаметно работающие задачи. Работающий backend можно закрыть явным действием после завершения/остановки его задач. Второй детерминированный backend для тестов доказывает заменяемость, полноценный второй провайдер здесь не реализуется.

### 3. Диалоги и выполнение

N означает отсутствие искусственного ограничения числа диалогов: каталог загружается страницами, история — по требованию. У каждого диалога свои сообщения, draft, scroll anchor, выбранная модель, настройки и pending requests. Список показывает название, свежесть, непрочитанное и состояния «работает / нужен ответ / ошибка»; доступны создание, поиск, открытие, переименование, архив и восстановление.

По умолчанию проектируется возможность одновременных задач в разных диалогах при поддержке backend. На диалог — один активный turn. При занятом диалоге отправка выбирает явно показанный режим «уточнить текущую задачу» при поддержке backend либо «отправить после завершения». Невозможность backend выполнять несколько задач выражается видимой очередью. Переключение вкладки и закрытие UI не отменяет задачи.

Все диалоги одного мира используют его workspace. UI не обещает файловую изоляцию между параллельными задачами; индикатор показывает общий workspace. Автоматические worktrees/копии мира не создаются. При смене мира закрывается его соединение, очереди не переносятся, поздние события не попадают в новый мир. История Codex остаётся у Codex; локально сохраняются только UI-настройки и черновики с namespace мира/backend/thread.

### 4. Полнота возможностей Codex

Перед реализацией адаптера составляется полная матрица команд поддерживаемой версии CLI, включая условные и экспериментальные. Для каждой строки: источник/версия, назначение, UI-вход, контрактное действие, подтверждённый RPC или локальная реализация, требования доступности и проверка. Будущие команды не считаются автоматически поддержанными.

Группы обязательного охвата:

| Группа | Представление |
|---|---|
| Диалоги | Новый, продолжить, переименовать, архивировать, fork и другие объявленные операции |
| Модель | Каталог моделей, reasoning effort и service tier при поддержке; действующее значение видно рядом с вводом |
| Режим работы | Plan/обычная работа, разрешения и sandbox в пределах политики backend |
| Контекст | Прикрепление поддерживаемых ресурсов, compact, usage/status, diff и review |
| Расширения | Skills, MCP, приложения и другие команды версии через descriptors и специализированные панели при необходимости |
| Сервис | Аккаунт, лимиты, подключение, диагностика, справка, настройки и действия внешних приложений |

Это начальные группы, а не замена полной матрице. Все технически реализуемые команды базовой версии должны работать; «не реализовано» не является допустимым итогом приёмки. Для ограничений протокола/платформы остаётся видимое объяснение и внешний переход, если он возможен. Отсутствие функции в конкретном runtime отражается динамически. Полнота здесь означает полный учёт команд и реализацию доступных действий, а не обещание идентичной работе любого будущего CLI.

Согласованное исключение (2026-10-19): `/cd` и `/worktree` не входят в функциональный паритет. Рабочая область остаётся привязанной к миру; эти действия показывают объяснение и возможность продолжить работу во внешнем CLI. Это продуктовое исключение, а не отсутствие возможностей протокола. Флаги/подкоманды CLI, меняющие cwd или создающие worktree, подчиняются тому же ограничению.

Меню открывается кнопкой или сочетанием клавиш, содержит поиск и категории. `/` может открывать то же меню, но не обязателен. Текст подтверждения не парсится как управляющая команда. Список моделей берётся у backend, доступность проверяется также ответом на запуск; при ошибке сохраняются текст и выбранное значение. Изменение модели/effort во время работы помечается «для следующего сообщения» и не меняет уже выполняемый turn. Глобальная конфигурация не перезаписывается незаметно.

### 5. Богатая лента как модель событий

Лента состоит из типизированных элементов со стабильными id: сообщения пользователя и агента, доступные summaries, план/шаги, web actions, tool calls, execution, file changes, child tasks, compaction, review, usage, ошибки и запросы ввода. Backend нормализует события; окончательный снимок элемента заменяет накопленную временную версию без дублирования.

Карточка показывает понятное действие, объект, состояние и elapsed time. Для web: поисковый запрос, URL/домен и полученные ссылки, когда они предоставлены. Для инструмента: имя, сервер, аргументы, прогресс и результат. Для команды: команда, cwd, живой вывод, завершение и exit code. Для файлов: пути, тип изменений и diff. Для дочерних задач: роль/название, статус и доступная связь с диалогом. Отсутствующие данные не синтезируются.

Состояния: queued, running, waiting-for-user, completed, failed, interrupted, disconnected. Сосуществующие действия не сворачиваются в один глобальный индикатор «думает». Длинные результаты свёрнуты, но доступны по раскрытию; выделение/копирование, code blocks и ссылки поддерживаются. Неизвестный информационный элемент получает generic-карточку; неизвестный обязательный запрос завершается явным неподдерживаемым ответом, без зависания и автоодобрения.

Подтверждения и вопросы находятся рядом с соответствующим действием. Фокус не перескакивает на появившуюся кнопку; Enter из composer не одобряет запрос. После ответа кнопки блокируются до результата, повторный ответ не отправляется. Поддерживаются выбор вариантов, свободный текст и формы MCP в пределах descriptors. Для запросов с внешним OAuth/браузером показывается явный переход.

### 6. Внешний вид и ввод

Уточнение пользователя 2026-10-19: вкладки размещаются в одном родном GuiChat, без открытия отдельного экрана для Codex. Forge-адаптер подменяет только точный vanilla GuiChat на его подкласс при открытии, сохраняя начальный текст (включая `/`). Переключение вкладок меняет режим того же экземпляра; обычный ввод делегируется vanilla, ввод агента полностью перехватывается. Ширина ограничивается областью игрового чата. Первый запрос сам подключает backend и создаёт диалог, повторный Enter во время запуска игнорируется, черновик сохраняется при ошибке и изменениях во время ожидания.

Основной режим — панель в области чата поверх мира, с кнопкой разворота. Родной пиксельный шрифт, прямые углы, сдержанный полупрозрачный угольный фон, светлый основной текст, один акцент; цвет всегда дополняется словом/значком. Базовая сетка отступов 4 logical px; высота строк определяется метриками шрифта. Размеры и прозрачность учитывают настройки чата. Узкий экран скрывает список диалогов в переключатель, но сохраняет доступ к нему.

```text
[Чат] [Codex]                 [Диалоги • 3] [+] [↗]
 База · работает              [Модель ▾] [Действия]
 › Найди пример и построй склад
 ✓ Поиск в интернете · 3 результата             ▸
 ● Инструмент · world.inspect                   ▾
   Осмотр участка…
 ! Изменить файлы — нужен ответ
   [Разрешить] [Отклонить] [Подробности]
 ────────────────────────────────────────────────
 › Уточнить задачу…                  [Остановить]
```

Enter отправляет, Shift+Enter создаёт строку; Tab перемещает фокус, стрелки выбирают пункты меню, Escape закрывает верхний popup, затем панель. Остановка отдельным действием. Переключение диалогов сохраняет курсор/черновик/прокрутку. Автопрокрутка работает только у конца ленты; при чтении выше появляется «Новые события». Отрисовка виртуализирована, перенос строк кешируется и пересчитывается при изменении ширины/текста, а не всей истории каждый кадр.

### 7. Проверка архитектуры и приёмка

Исключение по прямому разрешению пользователя 2026-10-19: агент самостоятельно отлаживает первую версию, включая игру, живой ответ backend и UI. Общие ограничения ниже продолжают действовать для последующих версий. Результаты разрешённой проверки фиксируются по фактическим наблюдениям агента.

Диагностика двух вылетов первой версии показала `UnsatisfiedLinkError` в OpenAL, включая вылет до входа в мир. Vanilla SoundManager запускает асинхронный загрузчик без флага loading; повторная загрузка ресурсов может создать второй OpenAL-контекст. Точечный Forge coremod заменяет единственный Thread.start в SoundManager на start с ожиданием завершения загрузчика перед возвратом к перезагрузке. Звук не отключается; цена исправления — ожидание загрузки аудио при запуске/перезагрузке ресурсов. Трансформация ограничена SoundManager 1.7.10 и требует проверки при комбинации с другими coremods.

Контрактные сценарии запускаются на Codex-адаптере с записанными протокольными fixtures и на независимом fake backend. Проверяются interleaved events нескольких threads, reconnect, ответы на запросы, смена модели, pagination, восстановление истории без дублей и неизвестные события. Граф Gradle проверяет отсутствие запрещённых зависимостей.

Агент выполняет сборку, статический анализ и изолированные автоматические тесты на fake backend/fixtures, включая headless-проверки 100 диалогов и 10 000 элементов истории. Все runtime-проверки в игре или с живым backend выполняет пользователь. Агент не запускает игру, не автоматизирует её интерфейс и не собирает скриншоты для приёмки без нового прямого запроса. Такие действия не включаются в tasks агента, их отсутствие не блокирует реализацию.

Визуальные требования к продукту сохраняются: компактный/развёрнутый режимы, разные GUI scale, узкое окно, кириллица, длинный вывод, формы и два работающих диалога; отсутствие обрезанных кнопок, перекрытий ввода и потерянного фокуса. Сценарий от открытия диалога до tool/web activity, подтверждения и результата не требует служебных команд. Подтверждённые runtime-результаты документируются только по обратной связи пользователя.

## Risks / Trade-offs

- Изменения протокола → фиксированная проверенная базовая версия, контрактные fixtures и явная диагностика несовместимости.
- Различия backend → capabilities вместо Codex-типов в UI; отсутствие поля не подменяется вымышленными данными.
- Перегрузка маленького чата → сворачиваемые подробности, разворот, адаптивная компоновка и виртуализация.
- Параллельная запись в общий мир → общий workspace явно виден; межагентная транзакционная изоляция не обещается.
- Моды, изменяющие чат → runtime-совместимость подтверждает пользователь; агент не объявляет непроверенные комбинации проверенными.
- Объём паритета команд → матрица и проверки каждой строки; UI не выдаёт заглушки за поддержку.

## Migration Plan

Сначала выделить контракты и покрыть текущий транспорт fixtures, затем перенести Codex за adapter, добавить многодиалоговое состояние, UI и подключение Forge. Сохранить существующие workspace и серверную историю. Старые команды заменить меню, обновить README. Миграция данных Codex не требуется. Для rollback использовать предыдущую сборку; локальное UI-состояние хранить версионированно и отдельно от истории backend, чтобы его можно было игнорировать без повреждения диалогов.


## Уточнение пользователя: CLI-first flow (2026-10-19)

Сохранить текущее оформление UI, карточки и встраивание в игровой чат. Основной
ввод — текст и slash-команды с подсказками, стрелками, Tab и Enter. Постоянные
кнопки New/Model/Actions/Send/Stop/Connect убрать. Оставить переключение игрового
чата и компактного/развёрнутого представления; формы/подтверждения показывать
контекстно. Неизвестные команды не отправлять модели. Это уточнение заменяет
прежнее решение о необязательных slash-командах и основном управлении кнопками.
